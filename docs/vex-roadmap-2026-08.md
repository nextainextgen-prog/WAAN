### เฟส 0.5 เสร็จแล้ว — ตัวตนเดียว ผูกได้หลายบัญชี

**สิ่งที่พบตอนสำรวจ (ทำให้งานเล็กลงกว่าที่คิด)**
- `KikiChat` ไม่มีคอลัมน์ `chatId` มาแต่แรก → ประวัติเป็นสายเดียวรวมกันอยู่แล้ว ทักช่องไหนก็ต่อเรื่องเดิมได้ทันที ไม่ต้องรื้ออะไร

- `kiki.ts`: `ownerAccounts()` / `isOwnerAccount()` / `linkOwnerAccount()` / `unlinkOwnerAccount()` เก็บที่ Setting `kiki_owner_accounts` = `["telegram:<id>", "discord:<id>"]` · seed อัตโนมัติจาก `kiki_owner_id` เดิมตอนถูกเรียกครั้งแรก · `getKikiOwnerId()` คงไว้ ของเดิมไม่พัง

**ตา (เฟส 4)** — `vex-eyes.mjs` ดักข้อความ Telegram ขาเข้า → ท่อเหตุการณ์กลาง
ตัวให้คะแนน 3 แกน (ด่วน · ใครพูด · ขัดจังหวะแพงไหม — อ่านปฏิทินจริง+เวลา+อยู่ในสายไหม)

**มือ (เฟส 5)** — เรียนสไตล์การคุยรายคนจากประวัติแชทจริง (ไม่ให้เจ้าของมานั่งสอน)
ความไว้ใจ 0/1/2 เริ่มทุกคนที่ 1 · ถอนได้ใน 30 วิ (ลบข้อความจริงใน Telegram)
จำกัด 20 ข้อความ/ชม. + เว้น 8 วิ กันบัญชีโดนแบน · หาคนไม่เจอ/กำกวม = ถามกลับ ห้ามเดา

**บั๊ก 2 ตัวที่เจอจากการใช้จริง (ไม่ใช่จากเทส)**
1. `\b` ของ JS ใช้กับภาษาไทยไม่ได้ (อักษรไทยนับเป็น non-word ทั้งหมด) →
   **"Vex พอ" สั่งหยุดไม่ติดเลย** ทั้งที่เป็นคำสั่งสำคัญที่สุด
   แก้เป็น lookahead `(?![\u0E01-\u0E4F])` · เทส 21 เคสผ่าน รวม "พอดีเลย/พอใจ/หยุดรถ" ที่ต้องไม่ติด
2. อ่าน log ของจริงวันแรกเจอว่า **เสียงทีวีที่บังเอิญมีคำว่า "Vex" ปลุกสำเร็จ**
   แล้วหน้าต่างคุย 30 วิ ทำให้เสียงรบกวนถัดมาถูกนับเป็นคำสั่งทั้งหมด ("ติ๊กต็อก บูม บูม")
   → หน้าต่างคุยแปลว่า "ไม่ต้องเรียกชื่อซ้ำ" **ไม่ได้แปลว่า "รับทุกเสียงที่ได้ยิน"**
   ตอนนี้ทุกประโยคต้องผ่านตัวกรอง "พูดกับเราไหม" ยกเว้นเรียกชื่อพร้อมคำสั่งในประโยคเดียว

**ข้อจำกัดที่ต้องรู้: โควตา Gemini TTS**
วันแรกใช้เสียงหนักมาก (เทียบ 30 เสียง + เทสทั้งวัน) → **TTS ตอบ HTTP 429 โควตาหมด**
สมองกับการถอดเสียงยังปกติ (คนละโควตา) แปลว่า **Vex ยังฟังและคิดได้ แต่พูดไม่ได้ชั่วคราว**
ใส่ทางถอยแล้ว: แปลงเป็นเสียงไม่ได้ = ลงห้อง `#vex` พร้อมสัญลักษณ์ 🔇 แทน ไม่ปล่อยให้คำตอบหายเงียบ
ถ้าจะใช้เสียงหนักทุกวัน ต้องเปิด billing ของ Google AI Studio (~0.76 บาท/1,000 ตัวอักษร)

### เฟส 2 เสร็จแล้ว — บอทอยู่ในห้องเสียง + ชั้นเลือกปลายทาง

**สถาปัตยกรรม: กล่องขาออก ไม่ใช่ให้ท่อยิง cron เอง**
เว็บ (ที่มีสมองกับ cron) กับท่อ Discord เป็นคนละโปรเซส และ "เจ้าของอยู่ในสายไหม" มีแต่ท่อที่รู้
→ เว็บหย่อนงานลงตาราง `VexOutbox` แล้วท่อมาหยิบไปส่งเอง (ท่อรายงาน presence กลับมาทุก 5 วิ)
ได้ของแถมที่จำเป็น: เจ้าของออกจากห้อง = ของค้างในกล่องรอจนกลับมา ไม่หายไปไหน

| ส่วน | ไฟล์ |
|---|---|
| ตัดสินปลายทาง + presence + ย่อเป็นภาษาพูด | `src/lib/kiki-outbox.ts` |
| กล่องขาออกให้ท่อมาหยิบ | `src/app/api/kiki/outbox/route.ts` |
| แปลงข้อความเป็นเสียงให้ท่อ (ท่อไม่ต้องรู้จักโมเดล) | `src/app/api/kiki/tts/route.ts` |
| เข้าห้องเสียง + คิวพูด + วนหยิบงาน | `scripts/kiki-discord.mjs` |
| รันเองตอนเปิดเครื่อง | LaunchAgent `com.changoh.vexdiscord` (KeepAlive) |

**กติกาที่บังคับไว้ในโค้ด**
- `vex_voice_announce` **ค่าเริ่มต้นปิด** — สั่งเปิดด้วยปากเท่านั้น (intent `voice_announce`)
  ปิดอยู่ = `routeProactive()` ไม่แตะ Discord เลยแม้แต่นิดเดียว
- **Telegram ได้ของครบเหมือนเดิมเสมอ** ไม่ว่าอะไรจะเกิดขึ้น — Discord เป็นแค่สำเนาที่เพิ่มเข้ามา
- **ห้ามพูดใส่ห้องเปล่า** — ไม่อยู่ในสาย = งานเสียงค้างในกล่อง ไม่นับเป็น tries ที่ล้มเหลว
  ออกจากห้องกลางประโยค = `player.stop()` ทันที
- presence เก่าเกิน 3 นาที = ถือว่าไม่อยู่ (ท่ออาจตายไปแล้ว — ดีกว่าพูดใส่ห้องเปล่า)
- พูดทับกันไม่ได้ (`speaking` lock) · เสียงหยิบทีละชิ้น ข้อความหยิบได้ทีละ 5

**เสียงที่พูดออกมาไม่ใช่ข้อความดิบ** — `toSpeech()` ย่อด้วยสมองก่อนเสมอ:
ทวนหัวเรื่องขึ้นต้น (จอดับ มองไม่เห็นว่าตอบเรื่องไหน) · 1-2 ประโยค · ห้ามอ่านลิสต์/ตัวเลขทุกตัว ·
รายละเอียดเต็มไปอยู่ในห้อง `#vex` ให้ย้อนดู

**กับดักที่เสียเวลาไปมาก: `DISCORD_GUILD_ID` ใน .env ผิด**

- `job_status` ที่ reply ผลงานเก่า = ตอบจากผลนั้น **ห้ามพูดว่า "ไม่มีงานค้าง"**

เทสจริงผ่าน: โจทย์ที่ส่งออกกลายเป็น *"หาตัวต่อจอ 2 จอ (USB-C/HDMI hub…) ราคาไม่เกิน 500 บาท ที่ขายในไทย
เสนอมาหลายตัวเลือกพร้อมชื่อรุ่น ราคา และลิงก์ร้าน"* + `parent` ผูกกลับงานเดิมถูกตัว ·
ถาม "งานถึงไหนแล้ว"/"เสร็จยัง" ขณะ reply ผลเก่า → ตอบจากผลจริง ไม่พูดว่าว่าง

**B3. ผลงาน Hermes ลงท้าย "ค่ะ" — ผลดิบออกแชทตรง ๆ ไม่ผ่านชั้นเรียบเรียง**
`cron/route.ts` ต่อสตริง `` `งานที่ฝากไว้เสร็จแล้วครับ...\n\n${d.body}` `` — ตัวรับงานเป็นคนละตัวกับ Vex
→ ครอบด้วย `askKiki` ก่อนส่งเสมอ โดยบังคับว่า **ตัวเลข ราคา ชื่อรุ่น ลิงก์ ต้องยกมาครบเป๊ะ ห้ามแต่งเพิ่ม**
และถ้าผลที่ได้เป็นแค่คำถามกลับ ให้บอกเจ้าของตรง ๆ ว่ารอบนี้ยังไม่ได้ของ

เทสจริง 2 เคสผ่าน: ผลดิบที่เป็นคำถามลงท้าย "ค่ะ" → ออกมาเป็น *"รอบนี้ยังไม่ได้ของครับ ผู้ช่วยเบื้องหลังส่งกลับมาเป็นคำถามล้วน ๆ…"* ·
ผลดิบที่มีของจริง → ตัวเลข/ลิงก์ครบทั้ง 7 จุด ไม่มีหายสักตัว ไม่มีคำว่า "ค่ะ"

บอกตรง ๆ ว่ามันคุยกับเจ้าของไม่ได้ คำถามที่เขียนจะไม่มีใครตอบ · กำกวม = ตีความแล้วลงมือเลย
**ผล A/B ไม่ชี้ขาด:** ยิงโจทย์กำกวมตัวเดียวกันเข้าทั้ง guard เก่าและใหม่ — **ได้ของจริงทั้งคู่**
แปลว่าอาการ "ถามกลับแล้วจบ" ไม่เสถียร ไม่ได้เกิดจาก guard อย่างเดียว

**1. watchdog ตายเงียบ ๆ มา 2 ชั่วโมง — ตัวที่คอยกู้ระบบ กู้ตัวเองไม่ได้**

`const SESSION_FILE` ถูกประกาศ **ใต้** ลูป top-level ที่เรียกใช้มัน — ฟังก์ชัน hoist ได้ แต่ `const` ติด TDZ
เข้ามาจากคอมมิต `4d27c5e` (11:13) แล้วเซสชันจบตอน 11:18 เลยไม่ทันเห็น
→ ย้ายขึ้นไปเหนือลูป · **กติกาที่ได้: สคริปต์ที่รันด้วย StartInterval ต้อง `node --check` + รันจริงดูโค้ดออกทุกครั้ง ไม่งั้นตายแล้วไม่มีใครรู้**

**2. watchdog กล่าวหาผิดตัว แล้วสั่งงานเจ้าของฟรี ๆ**
เว็บล่มเมื่อเช้า → ทุก service พ่น `fetch failed` พร้อมกัน → `SOFTERR` จับได้ครบ 3 รอบ →
สรุปว่า **"เซสชัน REFUND หมดอายุ"** แล้วยิงเข้า Discord ทั้งเสียงและข้อความให้ไปรัน `thunder:auth`

→ แยก `AUTHERR` (หลักฐานตรง เชื่อได้เสมอ) ออกจาก `SOFTERR` (แค่ต่อไม่ติด เชื่อได้ต่อเมื่อเว็บเรายังดี)
**นี่คือกับดักข้อ "web ล่ม = ทุกอย่างพัง" ที่จดไว้แล้ว แต่ watchdog ไม่ได้เอากฎนั้นมาใช้กับตัวเอง**

**3. การ์ดมอนิเตอร์ยังแช่แข็งเว็บอยู่ — เมื่อวานแก้ไปแค่ครึ่งเดียว**
วัดจริงหลังเว็บขึ้น 83 นาที: `/api/kiki/monitor` เร็ว 54 ครั้ง แต่**ช้า 23 ครั้ง 4-32 วินาที**
รากปัญหา 3 ชั้นซ้อนกัน:
- `readUsage()` เป็น `readFileSync` ล้วน → ไม่ได้แค่ช้า แต่ **บล็อก event loop ทั้งเว็บ**
  (หลักฐาน: `POST /api/kiki/ingest 401 in 10.8s` ทั้งที่ตัวงานเองใช้ 184 ms — ที่เหลือคือรอคิว)
- อ่านไฟล์ **3 รอบ** (session/week/today แยกกันคนละรอบ) ทั้งที่ข้อมูลชุดเดียวกัน
- มีคนอ่านของหนักนี้ **2 ทางแยกกัน** — การ์ด (แคช 5 นาที) กับตัวเช็คใกล้เต็ม (`readUsage()` ตรง ๆ ไม่ผ่านแคชเลย)

→ ยกเครื่อง `usage.ts`: อ่านรอบเดียว + **แคชรายไฟล์ด้วย mtime+size** (log ที่เขียนจบแล้วไม่มีวันเปลี่ยน
รอบต่อไปจึงอ่านใหม่เฉพาะไฟล์ที่กำลังถูกเขียนจริง ๆ) + async I/O ทั้งเส้น
+ `readUsageCached()` เป็นทางเข้าเดียว มี singleflight กันยิงพร้อมกันตอนเว็บเพิ่งขึ้น

เจอเพิ่มตอนวัดผลจริง: แคชอยู่ในหน่วยความจำ **หายทุกครั้งที่เว็บรีสตาร์ท**
และเว็บรีสตาร์ทบ่อยมาก (watchdog กู้ให้ · dev reload) — ตอนบูตคือช่วงเครื่องยุ่งที่สุดพอดี
